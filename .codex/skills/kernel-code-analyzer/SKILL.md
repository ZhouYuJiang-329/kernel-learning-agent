# Kernel Code Analyzer Skill

## 目标

对用户提供的内核代码，从三个维度给出完整分析：

1. **微观详解**：每个结构体字段、每条关键语句是什么意思、为什么这样写
2. **宏观定位**：这段代码属于哪个内核子系统、在哪些场景下被调用、解决什么实际问题
3. **调用链路**：从外部触发点到这段代码的完整路径，以及这段代码向下调用的路径

---

## 分析流程

### Step 0：用 kernel-graph MCP 工具查询源码（必须，不可跳过）

**在写任何分析文字之前，必须先调用 kernel-graph MCP 工具查询真实数据。** 靠记忆推断调用关系是不可靠的，内核版本之间差异很大，必须以实际代码为准。

对分析目标函数，依次执行以下查询（并行调用以节省时间）：

1. **定位源码**：`find_definition(函数名)` → 获取准确的文件路径和行号
2. **查结构体**：如果涉及关键结构体，`find_struct(结构体名)` → 获取所有字段定义
3. **向上调用链**：`call_chain_up(函数名, depth=4)` → 找出谁调用了它，追溯到顶层触发点
4. **向下调用链**：`call_chain_down(函数名, depth=3)` → 找出它调用了哪些函数
5. **补充细节**（按需）：对调用链中关键的中间函数，用 `find_definition` 或 `find_callers` 进一步确认

查询完成后，用查到的真实数据填充后续所有步骤。**不允许在没有 MCP 查询结果支撑的情况下写出调用链或文件路径。**

### Step 1：大白话总览 + 设计模型（首先输出，建立第一印象）

**在所有技术细节之前，先用平实语言介绍这个函数/结构体/宏，并强制补一段"如果让我自己设计它"的设计模型。** 目标是让读者在看控制流和逐行详解之前，先知道：这段代码最朴素是在解决什么问题、要处理哪些数据、为什么真实内核实现会变复杂。

输出时按下面四个问题组织；若写入 `learn/` 文档，推荐放在 `## 一、大白话总览` 下，用 `（a）/（b）/（c）/（d）` 小节。

**（a）为什么要设计它？**
内核遇到了什么问题，或者需要满足什么需求，才催生了这段代码的存在？
用"如果没有它，会发生什么"来反向说明动机。

**（b）如果让你自己设计它，第一反应应该是什么？**
这一段是必选的"设计模型桥接段"，不是源码复述。必须包含以下 6 块：

1. **一句话降级**
   - 不用复杂术语说明它最朴素是在解决什么问题。
   - 先把专有机制降级成普通动作：登记、查找、选择、搬运、校验、通知、释放、回滚。
   - 这句话必须贴合当前分析对象，不能复用固定模板。

2. **最小模型**
   - 先去掉与主线无关的复杂度，例如层级结构、并发/锁、配额/限流、硬件差异、性能优化、错误回滚和特殊配置。
   - 说明最简单情况下：输入是什么、核心数据是什么、出口状态是什么。
   - 能画图就画一个很小的 ASCII 图；图里的节点必须来自当前分析对象。
   - 不要使用固定图示。需要参考不同子系统的写法时，读取 `references/design-model-examples.md`。

3. **核心数据对象**
   - 列出 3-7 个关键结构体/字段。
   - 每个对象必须说明"它在这件事里扮演什么角色"，不要只解释字段字面含义。
   - 优先使用类比，例如"任务档案"、"参赛卡片"、"队列"、"账本"、"目录项"、"注册表"。

4. **真实复杂度从哪里来**
   - 说明为什么最小模型不够。
   - 复杂度通常来自：层级结构、状态机、并发/锁、硬件约束、性能优化、ABI/API 兼容、特殊配置。

5. **如果自己实现，大概步骤**
   - 先写正常路径。
   - 再写特殊分支。
   - 明确哪些树/链表/计数/状态位/引用计数要同步维护。
   - 明确最后有哪些外围副作用，如唤醒、调频、负载均衡、通知、回滚、释放资源。

6. **源码阅读 checklist**
   - 给用户一组问题，用来读后面的 `if`/`for`/字段。
   - 每个分支都应该能归类到 checklist 里的某一项，例如"这是特殊状态分流？这是更新账本？这是并发保护？这是失败回滚？"。

**按对象类型调整设计模型：**

- **分析函数时**：必须回答入口参数代表什么、主要改变哪些数据结构、正常路径是什么、特殊分支是什么、出口状态是什么、调用者为什么需要这个结果。
- **分析结构体时**：必须回答如果自己设计最少需要哪些字段、哪些字段表示身份/状态/统计/链接关系、谁初始化、谁读写、字段之间有什么不变量、哪些字段只是优化缓存。
- **分析调用链/path 时**：必须回答这条路径从什么事件开始、每一层把问题转换成什么、中间哪些状态变化、哪些条件会分叉、最终谁消费结果。

**（c）它是怎么设计的？**
核心思路是什么？用了什么关键机制或数据结构？
不要列举字段，而是说清楚"设计者的思路"——比如"用一个嵌入在 task_struct 里的单向链表来避免堆分配"，而不是"有一个 next 指针"。

**（d）它处理哪几种情况，每种情况分别做什么？**
如果函数有多条执行路径（根据不同条件走不同分支），逐一列出每种情况：
- 情况是什么（触发条件）
- 这种情况下做什么
- 为什么这种情况要这样处理

格式参考（实际写时用中文大白话，不要这么生硬）：
```
情况一：xxx 时
  → 做：yyy
  → 为什么：zzz

情况二：xxx 时
  → 做：yyy
  → 为什么：zzz
```

**写作要求**：
- 假设读者懂 C 语言和操作系统基础，但不熟悉这个具体模块
- 先讲"要处理什么数据"，再讲"源码怎么做"
- 先讲最小模型，再讲真实复杂度
- 不要一开始堆函数名、宏名和算法名；如果必须出现 EEVDF、PELT、RCU、锁、cgroup、bandwidth 等术语，先用一句话解释它在当前对象里的作用
- 优先使用小图、步骤清单、状态表和 checklist
- 每种情况要说清楚"触发条件 → 做法 → 原因"，三个都要有
- 不要把 Step 1 写成逐行解释；逐行解释放到后面的 Step 6

### Step 2：控制流骨架

**在大白话总览之后，用树形图把函数的 if/for/while 骨架画出来。** 目标是让读者一眼看清：整个函数有几条执行路径、每条路径的触发条件是什么、最终做了什么事。

**画法规则**：
- 顺序执行的步骤用 `│` 连接，垂直往下
- 分支用 `├─ [条件]` / `└─ [条件]` 展开
- 循环用 `【for/while 循环】` 标注，并标出所有 `break` / `return` / `continue` 的位置和原因
- 每个叶节点（最终动作）写一句话：**做了什么**，不展开细节
- 不写代码，不写行号，只写逻辑

**格式示例**（实际输出时替换为真实内容）：
```
function_name(参数)
│
├─ 【for 循环】xxx
│     ├─ [条件A] ...
│     │     → 做：yyy → break/return
│     └─ [条件B] ...
│           → 做：zzz → 继续循环
│
├─ 【if】条件X
│     ├─ 成立 → 做：aaa
│     └─ 不成立 → 跳过
│
└─ 最终动作：bbb
```

**要求**：
- 所有 `break` / `return` / `goto` 必须标出，并说明原因（"无等待者，直接返回" 而不是只写 "return"）
- 嵌套的 if/for 缩进表示，不要压平
- 并列的 if-else 用 `├─` / `└─` 区分，不要用序号列表代替

### Step 2.5：Mermaid 图示（按需，但命中条件时必须输出）

默认不强制画图。只有当图能显著降低理解成本时，才输出 `## Mermaid 图示` 小节；不命中条件时直接省略，不需要解释原因。

**必须画图的场景**：
- 用户明确要求“画图”“Mermaid”“流程图”“状态图”“调用链图”。
- 函数有 3 个以上关键阶段，且纯文字控制流不容易一眼看懂。
- 涉及状态迁移，例如 `state` / `on_rq` / `on_cpu` / `sched_delayed`。
- 涉及字段生命周期，例如初始化、入队、运行、出队、释放之间的字段含义变化。
- 涉及对象归属或层级关系，例如 task、entity、queue、device、driver、cgroup、owner/waiter。
- 涉及跨 CPU、锁顺序、唤醒/迁移、引用计数、资源初始化/回滚。

**图类型选择**：
- 主执行路径 / 分支流程：`flowchart TD`
- 字段生命周期 / 对象关系：`flowchart LR`
- 状态迁移：`stateDiagram-v2`
- 跨 CPU / 锁 / 唤醒 / 通知交互：`sequenceDiagram`

**约束**：
- Mermaid 是理解辅助，不替代 Step 2 的 ASCII 控制流骨架，也不替代 Step 5 的 ASCII 调用链。
- 只画主路径和关键分支，节点控制在 8-18 个。
- 节点名使用真实函数名/字段名 + 简短中文说明。
- 不画未经 MCP 查询、源码阅读或用户提供代码确认的调用关系。
- 不把逐行细节塞进图里；逐行细节仍放 Step 6。
- 需要参考写法时，读取 `references/mermaid-examples.md`；不要把示例中的函数名、字段名或路径原样复用到无关对象。

### Step 3：快速定位

基于 Step 0 的查询结果，用 5-10 行建立整体认知：
- 这段代码属于哪个子系统（调度器 / sysfs / kthread / 锁 / 热插拔 / 内存 / 中断 / ...）
- 它的核心职责是一句话能概括的什么
- 源码文件路径（来自 `find_definition` 的结果，格式：`> 源码位置：include/linux/xxx.h, kernel/xxx/xxx.c`）

### Step 4：宏观地位分析

回答"这段代码在内核中是什么角色"，从三个角度展开：

**（a）所属层次**
用层次图展示这段代码在内核架构中的位置。层次图必须使用当前分析对象真实所在路径，不要复用固定模板。

要求：
- 从外部事件、上层框架或所属子系统入口开始
- 中间层写清楚每一层把问题转交给谁
- 用 `[这段代码在这里]` 标出当前位置
- 下方继续写它依赖的底层机制、通用框架或硬件/固件接口
- 需要参考不同子系统的层次图写法时，读取 `references/architecture-and-trigger-examples.md`

**（b）触发场景**
列出 2-4 个具体、真实的触发场景，用"当...时"的格式。

要求：
- 每个场景必须有真实入口事件，例如用户态操作、内核事件、设备发现、定时器、任务状态变化或硬件/固件响应
- 必须说明经过哪条上层路径到达当前代码
- 场景必须来自当前分析对象的调用链、源码证据或用户提供上下文
- 不要写"被需要时调用"这类空话
- 不要复用固定例子；例子必须贴合当前分析对象


**（c）解决什么问题**
说清楚如果没有这段代码、或者这段代码有 bug，会发生什么后果。
这是理解"为什么它要这样设计"的关键视角。

### Step 5：完整调用链路

**数据来源**：直接使用 Step 0 中 `call_chain_up` 和 `call_chain_down` 的查询结果，不依赖记忆。如果查到的链路深度不够，补充调用 `find_callers` 或 `call_path_between` 来补全。

用 ASCII 树展示完整的调用路径，分两部分：

**（a）向上：谁调用了它（入口链）**
```
顶层触发点（用户操作 / 内核事件）
  └── 函数A()                    // 所在文件:行号
        └── 函数B()              // 所在文件:行号
              └── 函数C()        // 所在文件:行号
                    └── [当前分析的代码]
```

如果有多条入口路径，分别列出（例如读路径和写路径）。文件路径和行号来自 MCP 查询结果。

**（b）向下：它调用了什么（执行链）**
```
[当前分析的代码]
  ├── 分支A
  │     ├── helper_func1()       // 作用说明，来自 call_chain_down
  │     └── helper_func2()       // 作用说明
  └── 分支B
        └── another_func()       // 作用说明
```

对链路中每个关键函数，用注释说明它做什么，不需要递归展开每一个。

### Step 6：逐行/逐字段详解

这是分析的主体，格式参考 learn/ 目录下的文件风格：

**结构体字段**：每个字段单独解释，说明类型、含义、何时被设置、何时被读取。
可用对照表或逐字段注释格式；示例只说明写法，实际输出必须替换成当前结构体自己的字段：
```c
struct example_object {
    int id;                 // 身份字段：区分这是哪个对象
    unsigned long state;    // 状态字段：记录当前处于哪种阶段
    void *private;          // 资源字段：指向实际业务数据或下层对象
    struct list_head node;  // 链接字段：挂到所属集合
};
```

**函数逻辑**：对每个关键步骤编号，用注释说明"做了什么"和"为什么这样做"。
特别关注：
- 防御性检查（`WARN_ON`、`IS_ERR`）的触发条件
- 加锁/解锁的原因（为什么用 `raw_spin_lock_irqsave` 而不是 `spin_lock`）
- 原子操作的必要性
- 内存分配标志（`GFP_KERNEL` vs `GFP_ATOMIC`）的选择原因
- 失败路径的清理逻辑

**关键设计决策**：对代码中不明显的设计选择，单独解释"为什么不用更简单的方案"。
例如：
- 为什么要延迟释放，而不是立刻释放
- 为什么要先验证状态再修改字段
- 为什么失败路径要按初始化的反方向清理
- 为什么某个统计字段要和链表/树操作同步更新
- 为什么要通过回调/函数指针分发，而不是直接调用具体实现

### Step 7：关键概念补充

如果代码涉及需要额外背景才能理解的内核机制，在最后单独说明。优先按机制类型解释，再给具体例子：
- 从成员指针反推对象的模式（如 `container_of`）
- 延迟释放或读侧并发保护机制（如 RCU）
- 内核统一文件输出/属性读写框架（如 `seq_file`、sysfs/configfs）
- 暂停 CPU、跨 CPU 执行或调度类协作机制（如 stopper、stop_machine）
- 硬件/固件通信、寄存器访问或共享内存协议

不要把所有相关知识都塞进来，只补充理解当前代码必须知道的背景。

### Step 7.5（可选）：识别"通用框架"信号，追加实战使用模板节

分析过程中如果命中以下任一信号，说明当前分析对象不是某个驱动的私有逻辑，而是被多方复用的**通用框架**（如 configfs、sysfs、debugfs、kobject、workqueue）：

- `find_callers`/`search_functions` 显示注册入口函数被 **3 个以上互不相关的子系统/驱动目录**调用（不同 `drivers/xxx/`、`fs/xxx/` 路径）
- 核心结构体是"类型描述符"模式——一个结构体把多个回调函数指针+属性数组打包在一起（如 `config_item_type`、`file_operations`、`device_driver`、`kobj_type`），驱动的用法是"填好这个结构体再注册"
- 文档/注释中出现严格的调用顺序要求（"必须在 XXX 之前调用"），暗示有一套设计好的初始化步骤
- 本次分析前已经见过至少一个其他驱动使用同一套 API（如先分析了某驱动怎么用，再回头分析框架本身）

命中信号时，在 Step 6 逐行详解之后，追加一节「**N、实战：如何使用 XXX（通用步骤模板）**」，内容是"如果我自己要用这个框架，该准备哪些结构体/回调、按什么顺序注册"，不是对某个已有驱动代码的复述。写法要求：
- 每一步给最小可用的代码骨架（伪代码级别，允许用 `my_xxx` 占位），不要求是内核里真实存在的某段代码
- 每一步反向链接回前面 Step 3-7 里已经 MCP 验证过的具体结论（如"对应判断点二""对应五.1 节分析的顺序"），不能凭记忆编造新的框架行为
- 结尾用一个"顺序小结"把所有步骤串成一行流程图

不满足以上信号时，不加这一节——多数分析对象是具体业务逻辑，没有"给别人复用"的模板价值，强行加会显得空洞。

## 输出格式规范

参考 `learn/` 目录下已有文档的风格：

**文件头**
```markdown
# [函数名 / 结构体名] 详解

> 源码位置：`include/linux/xxx.h`, `kernel/xxx/xxx.c`
> [一句话说明这组代码的整体职责]
```

**章节编号**：用中文数字（一、二、三...），每节有明确标题

**调用链**：用缩进树形图，`└──` 和 `├──` 符号，重要路径加 `← 关键点` 注释

**代码块**：保留原始缩进，行内注释用中文，格式 `// 注释`

**对照表**：涉及多个选项对比时用 Markdown 表格

## 输出目标

每次分析**必须同时完成两件事**，缺一不可：

1. **在对话中输出完整分析**（供即时阅读）
2. **写入 `learn/` 文件**（持久存档，内容与对话输出完全一致，一字不改）

**文件路径规则（硬性约束：永远落在 `learn/` 目录下，不允许写到其他位置）**：
- 用户未指定路径时，自动推断：`learn/{subsystem}/{function_name}.md`
- subsystem 从函数名关键词推断（与 CLAUDE.md 预检查表一致）：
  - `fair`/`cfs`/`vruntime`/`pick_next`/`enqueue_task`/`schedule` → `sched`
  - `mpam`/`resctrl`/`rdtgroup`/`rdt` → `mpam`
  - 其他 → 询问用户子系统名，或放入 `learn/unclassified/`
- 用户指定了路径 → 若路径已在 `learn/` 下则直接使用；若指定路径**不在** `learn/` 下（如项目根目录、`.claude/memory/` 或某个既有的路线图文件如 `*_read_guide.md`），**拒绝写入该处**，改为按上述推断规则落到 `learn/{subsystem}/{function_name}.md`，并告知用户已改路径及原因
- **绝不**把详细分析内容写入或追加进 `kernel-reading-guide` 产出的路线图文件（`learn/{MODULE_KEY}/{MODULE_KEY}_read_guide.md`）——那是框架性文档，只应包含指向本 skill 产出文件的链接，不能内联调用链树/逐字段解析等内容
- 文件名：小写加下划线，如 `wait_task_inactive.md`
- 一组相关函数：合并到一个文件，用最顶层函数命名
